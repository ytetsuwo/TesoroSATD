# 来歴の厳密検証

照合で得た来歴と、それを裏付ける証拠の確実性を別々に管理する。
`out/tesoro_provenance.csv` の 4,981 行は維持し、監査は全行を対象にする。

## 検査内容

1. **個別の版で AST を検査**
   各コメントの `path_snapshot` と `snapshot_commit` を使う。
   履歴・別ファイル・変形したコメントを除外せず、取得失敗も記録する。
   非空白行すべてがコメントノード上にあるか、期待するメソッド本体または
   直上のドキュメントに属するかを検査する。
2. **本文行を blame とコミットで検証**
   従来の本文・blame・show 検査も来歴付き全行に実行する。
   厳密監査では区切り記号だけの SHA を本文の証拠にしない。
   blame の元ファイル・元行を保ち、その SHA の同じ位置に実際の行が存在するか、
   CSV の `path_at_commit` と元ファイルが一致するかを検査する。
   複数の SHA が本文を担当する場合は要確認にする。
3. **部分一致を確定扱いしない**
   コード部分は本文比較に使わない。Unicode を NFKC 正規化し、空白と外側の
   コメントマーカーを除いた、順序を保つ本文全体の一致を要求する。
   大文字小文字・内部の句読点は維持する。改変・記号のみ・関数所属の不確実性を
   自動で確定に格上げしない。
   同一行に複数のコメントがある場合は、行全体を連結せず AST のコメントノード単位で
   比較する。連続する行コメントや、同一行の複数コメントが dataset の1コメントを
   構成する場合だけ、順序を保った完全一致を認める。dataset が元コメントの
   接頭辞である場合は、長さにかかわらず `review` にする。短い一般語が長文の
   どこかに含まれるだけの場合は `mismatch` のままにする。空のドキュメントで
   記録した行範囲が閉じ行を含まない場合も `review` にする。

## 判定

- `confirmed`（確定）: 本文全体、期待する関数への所属、本文行の SHA と元位置が確認できた。
- `review`（要確認）: 改変、記号のみ、複数更新者、構文エラー、所属の不確実性など。
- `mismatch`（不一致）: 本文・コメント行・SHA・元位置について証拠と矛盾する。
- `unverifiable`（検証不能）: ファイル・版・blame など必要な証拠を取得できない。
- `unmapped`（未対応）: 記録された来歴がない。

これは**記録した本文行の最終更新者**の検証である。最初の導入コミットや、
同文のコピー間の唯一の起源を保証しない。現在の本文を導入したコミットは
`28_introduced.py` が別集計する（[導入コミット](introduced_commits.md)）。
メソッド名の照合だけでは、同名のオーバーロードや別クラスのメソッドを完全に区別できない。

## コマンドと出力

```bash
python3 scripts/05_verify.py --all-checks  # 従来の3検査を全来歴付き行に実行、失敗時1
python3 scripts/14_check_span.py --json    # AST検査、問題時1、要確認は報告のみ
python3 scripts/27_strict_audit.py         # 全行の厳密監査、判定を報告（通常は0）
python3 scripts/27_strict_audit.py --fail-on mismatch,unverifiable # 任意の品質ゲート
python3 scripts/04_export.py               # 同じCSVの厳密監査をsummary.mdに反映
```

- `out/strict_audit.jsonl`: コメントごとの本文差分、所属、blame とコミットの証拠。
- `out/strict_audit_summary.json` / `.md`: 来歴付き件数とは別の判定集計。
- `work/span_check.jsonl`: `14 --json` の出力。旧形式と異なり**コメント単位**。

監査の SHA-256 と対象 CSV が一致する場合だけ `out/summary.md` に結果を載せる。
`reproduce.sh` は従来の全件3検査で失敗時に停止し、厳密監査は不一致も含めて
報告する。厳密監査の不一致を自動修正したり、来歴から削除したりはしない。

## 全件検査で見つかったパスの修正

最初の全件3検査では本文・blame が 4,961 件すべて通過した一方、コミット中の
ファイル検査は 7 件失敗した。取得した版のパスを、改名前のコミット中のパスとして
記録していたためである。blame の `filename` を使うよう手動対応付けを修正した。

対象は `15634:0`、`15634:14`、`34588:0`、`10081:1`、`18158:0`、`16008:1`、
`784:0`。変更は `path_at_commit` と対応するリンクだけで、コメント本文・取得した版・
行範囲・SHA・来歴付き件数は変えていない。

再精査では、行番号が1行ずれていた `2992:53`（`// "pagename"` は 897 行）と
`2992:55`（`// "pageurl"` は 912 行）、および `15927:106`（`/*12*/` は 1306 行）を
`25_manual_fixes.py` に追記して修正した。いずれも同じ関数・同じ blame SHA の
コメントで、本文と来歴付き件数は変えていない。

記号だけの履歴コメントは英数字の本文を持たないため、従来の本文部分文字列では
判定できない。ファイルの存在だけで通さず、blame の元ファイル・元行に同じ行が
存在することを検査する。コメントの閉じ記号を本文に混入させないこと、行コメント中の
文字列 `*/` は勝手に削らないことも回帰テストで確認している。

フォームフィード等で Python の `splitlines()` と Git の LF 行番号が異なる場合は、
CSV の行番号を Git の行番号へ変換する。コミット中の元行は Git の座標で比較し、
blame 本文中のフォームフィードも保持する。

